# Hardware validation — status

**Nothing in this directory has been compiled, simulated, or synthesized.**
This development environment has no C/C++ toolchain (`g++`/`clang++`/`cl`/`gcc`
all confirmed absent) and no Vivado/Vitis HLS installation. Every number in
this README's "still needed" list is a real gap, not a formality.

## What exists

- `hls/ema_det_gates.cpp` (+ `.h`, `nn_ops.h`, `hls_types.h`) — a
  literal, per-layer translation of `Block1 -> pool1 -> Block2 -> pool2 ->
  Gate1 -> Block3 -> pool3 -> Block4 -> pool4 -> Gate2` from
  `src/ema_det.py`, using **real trained weights** (BatchNorm folded into
  each conv) extracted by `src/export_hls_weights.py` from
  `results/emadet_final_best.pt` — not placeholder/synthetic values. This
  version allocates one full-size static buffer per layer (the BRAM
  overflow quantified below).
- `hls/main_tb.cpp` — a testbench comparing this C++ translation's Gate 1/2
  logits against the PyTorch model's actual outputs on 8 real test images
  (`hls/reference_io.csv`, `hls/input_test_*.bin`), also generated by
  `export_hls_weights.py`.
- `hls/block1_streaming.cpp` (+ `.h`) — a **line-buffer** (streaming)
  reimplementation of Block1 specifically, adapted from a proven working
  pattern found in a related prior project
  (`Bitirme/project_v2/preprocessing_filter/filter.cpp`'s 5-row Gaussian
  line buffer), but with Block1's real trained weights (BLOCK1_W/BLOCK1_B
  in `weights.h`) and "same" (zero) padding instead of that filter's fixed
  kernel and "valid" padding. Uses a 3-row line buffer (768B) instead of
  materializing the full 16x128x128 (512KB) output `ema_det_gates.cpp`
  allocates for this same layer — this is the AXI4-Stream/line-buffer
  restructuring the BRAM tally below calls for, done for Block1 (the
  single largest offender, 30.3% of the naive total) as a first step.
  Only Block1 is restructured so far; chaining this into Block2 as a fused
  dataflow pipeline is not yet done.
- `hls/block1_streaming_tb.cpp` — testbench for the above, validating
  every one of the 16x128x128 output values per test image against
  `src/export_hls_weights.py`'s Block1-only golden reference
  (`hls/block1_ref/*.bin`, gitignored, regenerate with
  `python ../src/export_hls_weights.py`).
- `hls/run_hls.tcl` — a Vivado/Vitis HLS project script (csim → csynth →
  cosim) for the Zynq-7020 target the paper targets. Written for the
  classic `vitis_hls`/`vivado_hls` command-line flow; the installed
  toolchain (Vitis 2025.2) uses the newer unified Vitis IDE instead, where
  HLS projects are "components" created via the GUI or `vitis-run`/Python
  scripting rather than this exact Tcl script — expect to adapt this step
  once inside the actual 2025.2 IDE.

## A known, unresolved design gap (not just "untested")

The current kernel allocates one full-size `static` buffer per layer. This
is a **functional/golden reference**, written to get the arithmetic right
first — it will not fit as synthesized today. `src/estimate_hls_bram.py`
gives a precise (arithmetic, not synthesized) tally of every declared
buffer at the `ap_fixed<16,6>` width used under `HLS_TARGET`:

```
buffer            shape             elements   KB @16b  % of total
block1_out        16x128x128         262,144     512.0       30.3%
block2a_out       32x64x64           131,072     256.0       15.2%
block2b_out       32x64x64           131,072     256.0       15.2%
pool1_out         16x64x64            65,536     128.0        7.6%
block3a_out       64x32x32            65,536     128.0        7.6%
block3b_out       64x32x32            65,536     128.0        7.6%
pool2_out         32x32x32            32,768      64.0        3.8%
block4a_out       128x16x16           32,768      64.0        3.8%
block4b_out       128x16x16           32,768      64.0        3.8%
gate1_conv_out    16x32x32            16,384      32.0        1.9%
pool3_out         64x16x16            16,384      32.0        1.9%
pool4_out         128x8x8              8,192      16.0        0.9%
gate2_conv_out    64x8x8               4,096       8.0        0.5%

Sum of all static buffers (if concurrently live): 1688.0 KB
XC7Z020 total BRAM capacity:                        630.0 KB
Ratio: 2.68x over budget (before counting weights.h, FIFOs, or any double-buffering)
```

**This is element-count x bit-width arithmetic on the declared array
shapes, not a synthesis result** — real BRAM mapping depends on how
Vivado HLS packs/partitions arrays, which cannot be known without running
`csynth_design`. But it does tell us where to prioritize the AXI4-Stream /
line-buffer restructuring: Block1 and Block2 alone (`block1_out` +
`block2a_out` + `block2b_out`) account for 60.7% of the naive total and
already exceed the entire chip's BRAM budget by themselves (1024 KB vs.
630 KB) — converting *just those three* to row-streamed line buffers
(rather than materializing the full feature map) should be the first
restructuring target, before touching Blocks 3/4 which are individually
much smaller. This priority ordering is the one concrete thing this
analysis can responsibly claim without a toolchain; the actual
LUT/BRAM/latency numbers still require running the real HLS flow (steps
1-5 above) on a machine that has it.
