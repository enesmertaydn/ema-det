# Hardware validation — status

**Nothing in this directory has been compiled, simulated, or synthesized.**
This development environment has no C/C++ toolchain (`g++`/`clang++`/`cl`/`gcc`
all confirmed absent) and no Vivado/Vitis HLS installation. Every number in
this README's "still needed" list is a real gap, not a formality.

## What exists

- `hls/ema_det_gates.cpp` (+ `.h`, `nn_ops.h`, `hls_types.h`) — a
  literal, per-layer translation of `Block1 -> pool1 -> Block2 -> pool2 ->
  Gate1 -> Block3 -> pool3 -> Block4 -> pool4 -> Gate2` from
  `src/ema_det.py`, using **real trained weights** (BatchNorm folded into
  each conv) extracted by `src/export_hls_weights.py` from
  `results/emadet_final_best.pt` — not placeholder/synthetic values.
- `hls/main_tb.cpp` — a testbench comparing this C++ translation's Gate 1/2
  logits against the PyTorch model's actual outputs on 8 real test images
  (`hls/reference_io.csv`, `hls/input_test_*.bin`), also generated by
  `export_hls_weights.py`.
- `hls/run_hls.tcl` — a Vivado/Vitis HLS project script (csim → csynth →
  cosim) for the Zynq-7020 target the paper targets.

## What is explicitly NOT done, and must happen in this order

1. **Compile and run `main_tb.cpp` in float** (`HLS_TARGET` undefined) on a
   machine with a C++ compiler. This is the first real correctness check —
   until it passes, nothing downstream should be trusted.
2. **C-simulate under Vitis/Vivado HLS** (`csim_design` in `run_hls.tcl`) —
   same check, but through the HLS tool's own simulator.
3. **Synthesize** (`csynth_design`) — only then do LUT/BRAM/latency numbers
   exist at all. `hls_types.h`'s `ap_fixed<16,6>` is an unvalidated starting
   guess, not a chosen operating point.
4. **C/RTL co-simulation** (`cosim_design`) against `reference_io.csv` in
   fixed point — the float translation passing (step 1) says nothing about
   whether `ap_fixed<16,6>` retains enough precision.
5. Only after step 4 passes does it make sense to report resource usage,
   power, or latency numbers in the paper.

## A known, unresolved design gap (not just "untested")

The current kernel allocates one full-size buffer per layer (e.g. Block1's
output alone is 16×128×128 — roughly 512 KB even at `ap_fixed<16,6>`,
against the Zynq-7020's ~613 KB total BRAM). This is a **functional/golden
reference**, written to get the arithmetic right first — it will not fit as
synthesized today. The paper's planned AXI4-Stream / line-buffer dataflow
restructuring is the actual fix, and should be designed using real
`csynth_design` resource reports (step 3 above) as feedback, not guessed at
before any synthesis has run once.
