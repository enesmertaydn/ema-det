**Block1's streaming kernel (`hls/block1_streaming.cpp`) is now fully
closed: real C-simulation (float and fixed-point), real synthesis, and
real C/RTL co-simulation, all passing.** This was all done from a plain
Windows machine with no C/C++ toolchain of its own, using Vitis Unified
IDE 2025.2's own bundled tools (see the iteration history below) — nothing
in this directory was ever compiled, simulated, or synthesized in the
*development* environment this repo's Python/paper work was otherwise done
in (no `g++`/`clang++`/`cl`/`gcc` there either). `ema_det_gates.cpp` (the
flat, non-streaming translation of the rest of the network) and Blocks~2
through~6 have not been run through any of these steps.

## Status: Block1's streaming kernel is fully verified — C/RTL cosim PASS

**2026-07-30, Vitis Unified IDE 2025.2, Zynq-7020 (`xc7z020clg484-1`), 10ns
clock target.** C/RTL co-simulation (`cosim_design` / "C/RTL COSIMULATION

the project's first real, end-to-end closed hardware result for any part
of EMA-Det: numerically verified in float and fixed point, resource
budget verified by real synthesis (not estimated), and now RTL-verified
by real co-simulation — nothing left unconfirmed for Block1 specifically.

  `python ../src/export_hls_weights.py`).
- `hls/run_hls.tcl` — a Vivado/Vitis HLS project script (csim → csynth →

`ema_det_gates.cpp`/`main_tb.cpp` (the flat, non-streaming translation

**Synthesis, iteration 1 (float, `HLS_TARGET` not defined — a config
mistake, not the intended target representation):** BRAM_18K 12/280 (4%),
but DSP 784/220 (**356%**) and LUT 117654/53200 (**221%**) — both wildly
over budget. Root cause: floating-point arithmetic is far more expensive
in hardware than fixed-point; this was never meant to be the shipped
representation.

**Synthesis, iteration 2 (`-DHLS_TARGET` added, so `FixedT`=`ap_fixed<16,6>`):**
Before that, C-sim caught a real accumulation-precision bug (accumulating
a MAC sum directly in FixedT rather than a wider `AccT` lost real
accuracy — see `hls_types.h`'s status note) — fixed, then measured
max|diff| ~1.26e-2/1.11e-2 (real input-quantization noise, not a further
bug; `block1_streaming_tb.cpp`'s tolerance was re-derived to 2e-2 from
this measurement). Resulting synthesis: **BRAM_18K 0/280 (0%)** — the
line-buffer restructuring fully eliminated Block1's BRAM problem — **LUT
28002/53200 (52%)**, comfortably under budget, but **DSP 304/220 (138%)**
still over. Root cause found: multiplying two pre-widened `AccT`
(32-bit) operands synthesizes a far more expensive multiplier per tap
than multiplying at native `FixedT` (16-bit) width and only widening the
*product* before accumulating. Fixed in `block1_streaming.cpp` and the
same pattern in `nn_ops.h` (`conv2d_same`, `conv1x1`, `fully_connected`) —
not yet re-synthesized to confirm.

## Why Block1's approach (full per-pixel parallelism) cannot just repeat for Block2+

Block1's kernel fully unrolls every MAC (`#pragma HLS UNROLL` on
`CH_LOOP`/`KY_LOOP`/`KX_LOOP`) so every output channel's every kernel tap
is computed in parallel, one physical multiplier per MAC, pipelined at
II=1. That cost 145 DSPs (out of 220 available) for Block1's
$16\times1\times3\times3 = 144$ MACs/pixel. This does **not** scale to the
rest of the network -- MACs/pixel grow with both channel counts (which
increase every block) and depend on nothing about Block1's own small
input-channel count:

| Layer | Cout x Cin x K^2 | MACs/pixel | DSPs needed at Block1's 1-per-MAC strategy |
|---|---|---|---|
| Block1 | 16x1x9 | 144 | 145 (fits: chip has 220) |
| Block2 (2nd conv) | 32x32x9 | 9,216 | ~42x the entire chip |
| Block4 (2nd conv) | 128x128x9 | 147,456 | ~670x the entire chip |
| Block6 (2nd conv) | 256x256x9 | 589,824 | ~2,680x the entire chip |

So the fact that Block1 fit is a consequence of Block1 specifically
having only 1 input channel, not evidence the same fully-parallel
strategy generalizes. **Block2 onward need a fundamentally different HLS
strategy**: a small, fixed-size, time-multiplexed MAC array (a systolic
array / PE array reused over many cycles per output, trading latency for
area) rather than one dedicated multiplier per MAC. This is exactly what
`Bitirme/project_v2/systolic_array_core/npu.cpp` (the 8x8 INT8 systolic
array found earlier in this project) is a building block for, and is
real, unstarted design work -- not yet attempted for any layer past
Block1.

## A known, unresolved design gap (not just "untested")

The current kernel allocates one full-size `static` buffer per layer. This
is a **functional/golden reference**, written to get the arithmetic right
first — it will not fit as synthesized today. `src/estimate_hls_bram.py`
gives a precise (arithmetic, not synthesized) tally of every declared
buffer at the `ap_fixed<16,6>` width used under `HLS_TARGET`:

```
buffer            shape             elements   KB @16b  % of total
block1_out        16x128x128         262,144     512.0       30.3%
block2a_out       32x64x64           131,072     256.0       15.2%
block2b_out       32x64x64           131,072     256.0       15.2%
pool1_out         16x64x64            65,536     128.0        7.6%
block3a_out       64x32x32            65,536     128.0        7.6%
block3b_out       64x32x32            65,536     128.0        7.6%
pool2_out         32x32x32            32,768      64.0        3.8%
block4a_out       128x16x16           32,768      64.0        3.8%
block4b_out       128x16x16           32,768      64.0        3.8%
gate1_conv_out    16x32x32            16,384      32.0        1.9%
pool3_out         64x16x16            16,384      32.0        1.9%
pool4_out         128x8x8              8,192      16.0        0.9%
gate2_conv_out    64x8x8               4,096       8.0        0.5%

Sum of all static buffers (if concurrently live): 1688.0 KB
XC7Z020 total BRAM capacity:                        630.0 KB
Ratio: 2.68x over budget (before counting weights.h, FIFOs, or any double-buffering)
```

**This is element-count x bit-width arithmetic on the declared array
shapes, not a synthesis result** — real BRAM mapping depends on how
Vivado HLS packs/partitions arrays, which cannot be known without running
`csynth_design`. But it does tell us where to prioritize the AXI4-Stream /
line-buffer restructuring: Block1 and Block2 alone (`block1_out` +
`block2a_out` + `block2b_out`) account for 60.7% of the naive total and
already exceed the entire chip's BRAM budget by themselves (1024 KB vs.
630 KB) — converting *just those three* to row-streamed line buffers
(rather than materializing the full feature map) should be the first
restructuring target, before touching Blocks 3/4 which are individually
much smaller. This priority ordering is the one concrete thing this
analysis can responsibly claim without a toolchain; the actual
LUT/BRAM/latency numbers still require running the real HLS flow (steps
1-5 above) on a machine that has it.
